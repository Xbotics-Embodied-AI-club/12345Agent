# 12345 智能工单 Agent Workshop 学员常见问题 FAQ


## 1. 这个项目是不是做一个聊天机器人？

不是。这个项目虽然也会使用大模型，但它的重点是帮助工作人员处理 12345 工单。

一条群众诉求进入系统后，需要经过诉求理解、工单生成、事项分类、承办单位推荐、人工审核和回复生成等步骤。每一步的结果都要传给下一步使用，而不是只回答一个问题就结束。

大家在设计作品时，要重点说明：

- 群众输入了什么；
- 系统从中提取了哪些信息；
- 系统为什么推荐某个类别或部门；
- 哪些结果需要工作人员确认；
- 最终生成了什么工单和回复草稿。

简单来说，我们要做的是一个“工单处理助手”，不是一个普通聊天窗口。


## 2. 群众提供的信息不完整，系统应该怎么办？

系统不能自己猜，应该把缺少的信息明确显示出来。

例如群众只说“小区门口垃圾很多”，但没有说小区名称、所在区域和具体位置。系统可以先提取“垃圾未清理”这个事件，同时标记“地点信息不完整”，再提醒工作人员补充。

比较合适的处理方式有三种：

1. 提示群众补充具体地点；
2. 交给工作人员人工确认；
3. 暂时生成工单草稿，但明显标注缺失字段，不能直接确认派单。

Workshop 演示时，建议专门准备一条信息不完整的样例，观察系统是否会暴露问题，而不是自动编造地点和时间。


## 3. 一个诉求同时涉及多个部门，应该推荐谁？

不要急着只选一个部门，可以先给出多个候选，并说明推荐理由。

例如占道经营可能涉及城市管理，也可能涉及交通安全；欠薪问题可能涉及人社部门，也可能需要属地单位协助。系统可以给出“主办候选”和“协办候选”，同时展示相关职责依据。

如果现有资料无法确定唯一主办单位，应直接标记“需要人工复核”。历史工单中以前由某个部门处理，只能作为参考，不能说明这次也一定归同一个部门。

演示时，学员需要讲清楚系统为什么推荐这些单位，以及最终选择仍由工作人员确认。



## 4. 模型生成的内容很通顺，是不是就说明结果正确？

不是。语言通顺只代表内容看起来合理，不代表事实和业务判断正确。

检查模型结果时，可以重点看四件事：

1. 有没有增加群众没有说过的时间、地点、金额或处理结果；
2. 工单内容有没有改变群众原本的诉求；
3. 分类和承办单位是否有目录、职责或政策依据；
4. 还没有实际办理时，回复中有没有写成“已经处理完成”。

如果出现以上问题，应由工作人员修改，或者让系统重新生成。项目中的人工审核步骤就是为了防止看起来很像正确答案的错误内容直接进入后续流程。


## 5. 已经安装了依赖，为什么运行时仍提示缺少某个包？

最常见的原因是：安装依赖和运行项目时，用的不是同一个 Python 环境。

本项目建议使用 `backend/venv`。如果电脑上同时装了系统 Python、Conda 和项目虚拟环境，终端或 VS Code 可能会选错。

可以按下面的顺序检查：

1. 确认当前目录是项目的 `backend`；
2. 激活 `backend/venv`；
3. 确认 VS Code 选择的也是这个环境；
4. 在这个环境中重新安装 `requirements.txt`；
5. 关闭旧终端，重新打开后再运行。

如果仍然失败，把完整报错发给讲师。不要只截最后一行，因为真正的原因通常出现在报错前面。

## 6. 页面能打开，但点击按钮没有结果怎么办？

页面能打开，并不代表后端接口一定正常。可以按下面的顺序排查：

1. 查看启动后端的终端是否仍在运行；
2. 打开 `http://127.0.0.1:8000/health`，确认健康检查是否成功；
3. 打开 `http://127.0.0.1:8000/docs`，确认接口文档能否访问；
4. 回忆是否修改过端口，页面和后端使用的端口是否一致；
5. 再操作一次按钮，观察后端终端是否出现新的报错。

如果首页显示“本地演示数据”，也要注意：这可能是后端接口请求失败后，页面使用了自带的演示内容，并不代表真实接口已经连接成功。

## 7. 没有大模型 API Key，还能完成 Workshop 吗？

可以。项目准备了本地引擎，即使没有 API Key，也可以完成文本诉求、工单生成、分类、回复和人工审核等基础流程。

页面显示 `local-engine` 时，说明当前使用的是本地引擎。它适合用来学习业务流程、熟悉页面和检查前后端是否正常。

如果已经填写 API Key，但仍然显示 `local-engine`，可以检查：

- Key 是否写在 `backend/.env`，而不是 `.env.example`；
- Key 是否仍然是 `replace_me`；
- 模型名称和服务地址是否正确；
- 修改 `.env` 后是否重新启动了后端。

查看结果中的 `source` 字段，也可以判断本次结果来自 `llm` 还是 `local-engine`。

## 8. 为什么知识库检索不到内容，或者检索结果看起来不准确？

检索不到内容时，先确认知识库中是否真的有数据。政策文件上传后，还需要填写文件名称、发布单位和所属分类，并完成入库，不能只完成文件上传。

如果知识库中有数据，但结果不准确，可以尝试：

1. 使用更清楚的关键词，例如把“这个事情谁管”改成“镜湖区道路占道经营由哪个部门处理”；
2. 检查政策或部门资料的分类是否填写正确；
3. 查看检索结果的来源和内容，而不是只看排序；
4. 确认当前资料是否适用于本地区和当前时间。

检索结果排在第一位，只表示它和问题比较相似，不代表它一定就是正确答案。最终仍要结合资料内容和人工判断。

## 9. 录音转写不准确，应该怎么办？

录音中有方言、背景噪声、多人同时说话或语速过快时，转写出现错误很正常。

处理时可以重点检查地点、姓名、时间、金额、电话号码和部门名称。这些内容一旦识别错误，可能会影响后续分类和工单生成。

比较合适的做法是：

- 保留原始录音和原始转写；
- 允许工作人员修改转写文字；
- 转写质量较差时，标记为需要人工确认；
- Workshop 现场先准备一段清晰、简短、经过授权的录音。

如果没有配置真实 ASR 服务，项目可能使用样例匹配或模拟转写。可以查看 `transcript_source`，确认文字实际来自哪里。

## 10. Workshop 最后最少要完成和展示什么？

最少要跑通一条完整的文本工单流程：

1. 输入一条群众诉求；
2. 展示提取出的事件、地点、诉求和缺失信息；
3. 生成一份可编辑的工单；
4. 展示事项分类、承办单位候选和推荐理由；
5. 由工作人员修改或确认结果；
6. 生成一份预回复或回访话术。

除了正常样例，建议再演示一条信息缺失或紧急事件样例，证明系统知道什么时候应该交给人工处理。

演示时不需要把所有高级功能都做完。先保证核心流程能运行、推荐有解释、结果能审核。录音、更多政策资料、复杂界面和数据看板都可以作为后续增强内容。
