第一部分 · 业务流
两条流程，一张工单

先分清真实业务，再设计辅助

Flow A · 真实行政业务流

群众来电 → 接线录入 → 生成工单 → 部门办理 → 回复 → 回访

包含受理、转派、部门办理与回访的完整链路。

Flow B · agent数据流

录音/文本 → 诉求理解 → 工单生成 → 分类与单位推荐 → 人工审核 → 结果录入 → 回复建议 → 人工确认

可用模拟数据演示，但各环节必须传递同一张工单的状态。

第三部分 · 总体原则
一句话原则
用确定性流程， 包住概率性模型。
反面案例 · 一次性的做法
群众来电→ 接线员录入→ 生成工单→ 转派职能部门→ 处理并回复→ 热线回访
把整条流程 + 诉求原文一股脑全塞给一个 LLM，让它一步到位出结果 ——
  • — 通用的多模态模型对方言的理解能力有限
  • — LLM 基于概率生成，结果不稳定，且没有地方行政法规作为依据
  • — LLM 对于复杂的长程问题处理能力有限，难以做到准确地拆解问题
▼ 点击问题揭晓三条理由
LLM
理解语言 · 生成草稿 · 比较候选
代码
校验字段 · 执行规则 · 控制权限
RAG
可更新 · 可引用的外部知识
人工
事实确认 · 转派与回复责任

第三部分 · LangGraph
State 贯穿 · Node 执行 · Edge 决策

LangGraph：把链升级为业务图

STATE
共享状态快照
贯穿原始输入、关键要素、候选部门、审核、错误与审计轨迹
NODE
原子执行节点
一次只做一项职责，并返回对 State 的局部更新
EDGE
路径与条件
读取 State 决定下一跳，组织顺序、分支、循环和重试
Main Graph · 赛题基础主线

→

→
03 · NODE
工单与推荐
生成工单、分类和承办单位
→
04 · NODE
人工审核
interrupt 暂停并等待确认
→
05 · NODE
结果与回复
录入办理结果，生成回访话术
分支 · Branch
missing_fields > 0 → 追问 Node；信息充分 → 继续生成
循环 · Loop
补充信息 ↺ 要素提取；审核驳回 ↺ 工单与推荐
重试 · Retry
工具失败 / 证据不足 → 限次重试 → 降级人工
LangGraph 的核心优势不是把流程画成图，而是让分支、循环、重试、暂停与恢复都成为可执行、可追踪的业务编排。

Page 34 · 回复生成
第三部分 · RAG 基础
不凭记忆回答，而是基于证据回答

什么是 RAG？

RAG，全称 Retrieval-Augmented Generation，中文通常叫「检索增强生成」——先检索可信知识，再把证据增强到上下文中，最后让模型基于证据生成结果。
01 · 检索 Retrieval
从知识库、政策文件、部门职责、历史案例中找到最相关的证据——版本有效、来源明确
02 · 增强 Augment
对证据做筛选、去重、排序、压缩和引用标记，整理成模型可直接使用的上下文
03 · 生成 Generate
在给定证据范围内完成分类、解释、回复草稿或建议；证据不足时明确提示不确定性

核心价值：

  • 提升事实准确性: 答案基于真实的参考资料，大大减少事实性错误。
  • 拓展知识边界：大模型可以获取训练数据之外的知识。
  • 降低成本：更新知识不需要重新训练大模型，只需要更新外部知识库

    第三部分 · RAG 必要性
    业务知识会变，而且必须给依据

    为何需要RAG，哪里需要RAG？

    适合 RAG
    • 事项分类目录、部门职责
    • 工单字段规范、质量检查规则
    • 政策文件、办理规范、批准模板
    • 脱敏历史案例仅用于相似情形参考
    不适合 RAG 替代
    • 当前来电事实
    • 流程状态
    • 最终行政判断
    • 真实办理结果
    RAG 用在“需要查外部依据”的环节：分类转派时查目录与部门职责，工单质检时查字段规范，回复辅助时查政策、办理规范与模板，相似案例用于提供参考。
